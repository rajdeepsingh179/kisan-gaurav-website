# Backend Reliability Report

Date: 2026-07-29

## Outcome

The critical Admin and commerce write paths now use transactional D1 batches and
database-enforced state transitions. No UI or authentication flow was changed.

Production deployment and the remote D1 migration were intentionally not run.

## Reliability controls

### Products

- Product, variants, variant removals, stock history, Media Library references,
  analytics, and audit logging commit in one D1 batch.
- Updating a missing product or a foreign/missing variant returns a stable error.
- Removed variants are archived, not hard-deleted, preserving order and inventory
  history.
- Re-adding an archived SKU restores the existing variant record.
- Product duplication, media links, and its audit entry are atomic.

### Media Library

- SHA-256 content hashing prevents new duplicate uploads.
- A scheduled backfill hashes existing assets and records legacy duplicates.
- Upload and replacement failures compensate R2 objects so metadata and objects
  do not silently diverge.
- Safe Delete performs an authoritative usage check inside the guarded database
  delete.
- R2 deletions are recorded in a durable cleanup queue and retried by the
  scheduled Worker.
- Usage counts continue to be calculated from the authoritative referencing
  tables and JSON content at read/delete time, avoiding a stale counter.

### Inventory

- All stock writes use an `inventory_mutations` ledger.
- Database triggers reject stale expected balances, unavailable variants, and
  negative resulting stock.
- The stock balance and `inventory_history` row are generated by the same
  transaction.
- Client-supplied stock deltas are no longer trusted.

### Orders

- Order, items, stock deductions, coupon redemption, notifications, saved
  address, verified-payment record, and payment-intent cleanup commit together.
- Stock and coupon limits are rechecked by database triggers during the write.
- Razorpay verification is idempotent through `processed_payments`.
- Invoice creation is compensated if the D1 transaction fails.
- Customer/admin cancellation restores inventory in the same transaction.
- Order transitions are optimistic and database-enforced; invalid or stale
  transitions are rejected.
- Duplicate active return requests are blocked.

### Validation and errors

- Order contact, address, cart quantity, duplicate line-item, return reason, and
  payment verification payloads are validated server-side.
- Product media duplication and archived-state normalization are validated.
- Category, coupon, CMS, settings, banner, homepage, digital-content, and SEO
  writes have server-side validation and stable not-found behavior.
- Database constraint failures map to stable HTTP status/code responses with a
  request ID; raw database internals are not exposed.

## Database changes

Migration: `worker/migrations/0014_backend_reliability.sql`

- Adds variant archival.
- Adds media content hashes and duplicate relationships.
- Adds R2 deletion queue and transaction assertions.
- Adds inventory mutation ledger and validation/application triggers.
- Adds order transition ledger and validation/application triggers.
- Adds verified-payment idempotency records.
- Adds coupon redemption and duplicate-return guards.

Rollback: `worker/rollbacks/0014_backend_reliability.rollback.sql`

The rollback removes new tables, triggers, and indexes. SQLite/D1 appended columns
remain inert because removing columns in-place is not a safe production rollback.

## Residual operational boundary

D1 and R2 cannot participate in one native cross-service ACID transaction. The
implementation therefore uses compensation for upload/invoice failures and a
durable retry queue for object deletion. This prevents partial database state and
makes any remaining R2 cleanup observable and retryable.
